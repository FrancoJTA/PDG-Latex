\subsection{MODEL CONTEXT PROTOCOL (MCP)}
\subsubsection{DEFINICIÓN Y ARQUITECTURA}

El \textit{Model Context Protocol} (MCP) es un protocolo abierto que estandariza la integración entre aplicaciones basadas en modelos de lenguaje de gran tamaño (\textit{large language models}, LLM) y fuentes de datos y herramientas externas \parencite{MCPSpec2026}. \textcite{Anthropic2024MCP} lo liberó en noviembre de 2024 porque aun los modelos más sofisticados quedaban aislados de los datos, y cada nueva fuente exigía una integración a medida. \textcite{Hou2025} lo caracterizan como un estándar unificado, bidireccional y con descubrimiento dinámico, abierto e independiente de la plataforma, y desde diciembre de 2025 lo gobierna la Agentic AI Foundation, bajo la Linux Foundation \parencite{MCPBlog2025AAIF}.

La arquitectura distingue tres participantes: los \textit{hosts}, aplicaciones LLM que inician las conexiones; los clientes, conectores dentro del host; y los servidores, que proveen contexto y capacidades \parencite{MCPSpec2026}. El host controla los permisos de sus clientes y aplica las políticas de seguridad y consentimiento; cada cliente mantiene una conexión aislada con un único servidor, que opera con responsabilidades acotadas \parencite{MCPSpec2025}. Los mensajes se codifican en JSON-RPC 2.0, un protocolo de llamada a procedimiento remoto ligero e independiente del transporte \parencite{JSONRPC2013}. La especificación define dos transportes: \textit{stdio}, en el que el cliente lanza el servidor como subproceso, y \textit{Streamable HTTP}, en el que el servidor atiende a múltiples clientes por un único \textit{endpoint} HTTP \parencite{MCPSpec2025}; la revisión vigente eliminó además las sesiones \parencite{MCPSpec2026}.

Un servidor ofrece tres primitivas: los recursos (\textit{resources}), contexto y datos; los \textit{prompts}, mensajes con plantilla; y las herramientas (\textit{tools}), funciones que el modelo ejecuta \parencite{MCPSpec2026}, controladas respectivamente por la aplicación, el usuario y el modelo \parencite{Ehtesham2025}. La herramienta es la primitiva central de este trabajo: declara nombre, descripción y un esquema de entrada en JSON Schema; el cliente la descubre con \texttt{tools/list} y la invoca con \texttt{tools/call}, y la especificación recomienda que siempre exista una persona con capacidad de denegar una invocación \parencite{MCPSpec2025}. El protocolo se apoya en la investigación sobre uso de herramientas por modelos de lenguaje. \textcite{Schick2023} entrenan un modelo capaz de decidir qué API llamar, con qué argumentos y cómo incorporar el resultado; \textcite{Qin2024} llevan el problema a más de 16\,000 API REST reales, y \textcite{Patil2024} identifican su modo de fallo característico, los argumentos incorrectos y la alucinación del uso de una API. Esos trabajos resuelven el lado del modelo; MCP estandariza el opuesto, cómo un servidor describe sus herramientas con esquemas explícitos para que cualquier host las descubra sin adaptadores a medida \parencite{Ehtesham2025}.

\subsubsection{INTEGRACIÓN DE SISTEMAS EMPRESARIALES CON MODELOS DE LENGUAJE}

Un ERP acumula datos transaccionales estructurados, actualizados a diario y sujetos a permisos por usuario. \textcite{Lewis2020} proponen la generación aumentada por recuperación (\textit{retrieval-augmented generation}, RAG), que complementa la memoria paramétrica del modelo con pasajes recuperados por similitud desde un índice vectorial. En un ERP, en cambio, la pregunta habitual (cuánto lleva certificado un centro de costo, qué riesgo estima el modelo) se responde con una consulta estructurada sobre la fuente vigente y con los permisos de quien pregunta. Entre los dos roles que plantea \textcite{Anthropic2024MCP}, exponer datos mediante servidores MCP o construir los clientes que los consumen, este proyecto toma el primero, con lo que la lógica de negocio y el control de acceso permanecen en el ERP\@.

El servidor del proyecto corre como proceso independiente y lo consumen clientes remotos, por lo que su transporte es Streamable HTTP, para el que la especificación define un flujo de autorización \parencite{MCPSpec2026}. En ese flujo el servidor MCP es servidor de recursos OAuth 2.1 y el cliente MCP, cliente OAuth. El servidor publica sus metadatos de recurso protegido \parencite{RFC9728}: ante una solicitud sin credenciales responde 401 con una cabecera que remite a ellos, donde declara su servidor de autorización. El token viaja como \textit{bearer} en cada solicitud y el servidor debe validar que fue emitido para él como audiencia \parencite{RFC8707}; un token inválido recibe 401 y un alcance insuficiente, 403 \parencite{MCPSpec2026}.

De ahí se desprende una consecuencia de diseño. Si el servidor MCP consulta API ascendentes, actúa ante ellas como cliente OAuth con un token separado y no debe reenviar el que recibió, para evitar el problema del delegado confundido \parencite{MCPSpec2026}. En el proyecto, el token que recibe el servidor MCP no puede viajar al ERP; el segundo token, del mismo usuario y con la audiencia del ERP, se obtiene con el intercambio de tokens que Keycloak implementa según el RFC~8693 \parencite{KeycloakTokenExchange}. La guía de \textcite{Keycloak2026MCP} documenta además el uso de Keycloak como servidor de autorización para MCP: como no soporta \textit{Resource Indicators}, la audiencia se fija con un \textit{Audience mapper} que incluye la URL del servidor MCP en el token.

La autorización no agota la seguridad. \textcite{Hou2025} sistematizan las amenazas por fase del ciclo de vida del servidor, entre ellas el robo de credenciales y los conflictos de nombres que llevan a ejecutar la herramienta equivocada, y \textcite{Radosevich2025} demuestran que modelos de primera línea pueden ser inducidos a usar herramientas MCP para ejecutar código malicioso o robar credenciales. La especificación establece que el servidor debe validar las entradas, controlar el acceso, limitar la tasa de invocaciones y sanear las salidas \parencite{MCPSpec2025}. En este proyecto eso se traduce en un servidor que expone únicamente consultas de lectura acotadas, sin nómina ni datos personales, con esquemas estrictos y los permisos del usuario que consulta. Así el servidor deja el ERP y las predicciones listos para un asistente conversacional futuro, cuya construcción queda fuera del alcance.
